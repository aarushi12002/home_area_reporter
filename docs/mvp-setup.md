# Home Area Reporter

ZIP-based research: What documented development, transit, public investment and parking activity is shaping this Seattle area?

Status: working Next.js website, local PostgreSQL persistence compatible with Neon, complete background permit ingestion for 98101–98105, canonical project construction, compact summary APIs, synchronized map/list presentation, full evidence report and an extension summary on Redfin/Zillow. Cloud Neon provisioning, durable jobs, live transit/alerts, complete public-project ingestion, parking connectors, payments and deployment remain planned.

## Product
- The website starts with **About this ZIP**: present-day local character, named workplaces/institutions, transport, groceries/shopping and medical care. This is distinct from proposed-change analysis and precedes the neighborhood snapshot. Selective highlights cover 98101–98105; outside-ZIP institutions carry a Nearby/postal-code label.
- Chrome popup on Redfin/Zillow with up to fifteen highlights, plus direct website ZIP entry and full report.
- Initial service-area records are 98101–98105. Adding coverage is configuration plus a jurisdiction connector, not a validation-regex change.
- Free area brief first. Pro pricing: $10 single property report / $20 five-report bundle; guest checkout. Pricing does not imply all source categories are integrated.
- No comparison or favorites in MVP.

## Stack
Implemented: Next.js App Router + JavaScript/ES modules, React, CSS, Drizzle schema definitions, committed PostgreSQL migrations, postgres.js, server-only Socrata adapters and Node tests. Local PostgreSQL uses the same `DATABASE_URL` boundary planned for Neon. Latitude/longitude and in-process Haversine ordering avoid a PostGIS requirement for the initial five ZIPs. A durable queue remains a later production decision; email and hosted payment remain later work.

## Current request flow
1. Direct website and extension accept only enabled initial service areas. Unsupported ZIPs receive an explicit response.
2. Extension reads available listing JSON-LD after the user invokes it, requests `GET /api/area-summary`, renders up to fifteen highlights, and links to `/report`. It stores only the reporter origin.
3. Scheduled/manual ingestion uses fixed official dataset endpoints, complete stable pagination, retries and one sync run per source/ZIP. Successful syncs replace records no longer present in the active query; failed syncs preserve earlier data.
4. Raw JSON, hashes, retrieval time, source event time and status are persisted. Normalization invalidates sentinel dates, classifies category/stage and retains traceable source links.
5. Project construction groups explicit references first and high-similarity same-address descriptions second, recording relationship type and confidence. Stale and undated projects remain stored but are hidden from the primary view.
6. `/api/area-summary` returns counts, at most fifteen highlights and a nullable `zipProfile`. The profile contains a short area/character summary, review dates and work/transport/shopping groups with official links and explicit in-ZIP/nearby/serves-area relations. It is also returned with permit-source outages so the website can still show present-day context. `/api/projects` returns paginated current evidence and coverage. `/api/projects/:id` returns a persistent project timeline. `/map` renders the compact same-origin extension map. The old `/api/report` remains as a compatibility/live diagnostic route.
7. Listing coordinates alter display ordering through proximity but are not persisted. Without coordinates, ranking uses stage, recency, scale and evidence confidence.
8. When the database is missing or has not ingested a supported area, the summary API uses a 15-minute live fallback and still returns only a compact response.
9. Printing uses the browser's print/save-PDF action. Sources remain online links; there is no server PDF or email delivery.

## Background versus click path

Eight background steps run outside the listing click: select enabled areas/sources, fetch all active pages, persist raw records, normalize, classify, resolve geography, group projects, and materialize ranking features. Five click-path steps remain: capture listing context, validate/resolve location, query persisted candidates, apply property-relative ranking, and render the compact result. Only validation, querying and ranking happen synchronously on the backend.

## Evidence and model boundaries
`lib/zip-profile.mjs` owns the manually reviewed current-area directory. It uses short name/address facts and original descriptive sentences from official company, institution, retailer and transit pages, with no listing-site copy, ratings, commute estimates, hours, salaries or automated POI/GTFS ingestion. This is editorial reference data, separate from source-record ingestion. Location addresses/postal codes remain in the response for review; mismatched postal codes are explicitly Nearby, and routes/stations are labeled as serving the area rather than guaranteeing proximity to a listing. Profiles are reviewed 2026-10-21 and suppressed from 2027-01-19; unsupported ZIPs, invalid dates and future-dated reviews return null. Existing permit/report behavior continues when a profile expires. Source expansion remains planned as described below; this directory does not establish a complete transit connector or complete business coverage.

No LLM is used. Official descriptions and original status are shown with conservative stage labels. Available source dates are event dates, not update dates; retrieval timestamps are separate. The shared summary builder adds `impactSummary` for both persistence and live fallback: conditional implications of recorded housing additions and building heights, with up to two supporting project links per topic. It uses all visible current projects before the highlight cap, excluding uncertain-stage and demolition-only projects from positive implications. Each factor includes a concise `takeaway` and a nullable `score`. The 1–5 record-support rubric adds one point each for a project, an official link, a numeric housing/height field, multiple projects and a permitted project; indirect economic implications are capped at 2. Missing evidence is `null` and displayed as an em dash. These are transparent ordinal record signals, not impact-severity, benefit, confidence-percentage or market-outlook scores. This legacy `impactSummary.items` score metadata remains in the API for compatibility; the website now uses grouped `decisionSignals` with concrete counts and single-plan metrics. Scoring methodology and data-origin explanations remain outside the snapshot UI. Individual project cards keep their city-record links, and partial source coverage remains visible.

Building-height mentions are descriptive evidence, not a confirmed change in height or view obstruction. Unit counts remain per project, never summed into a neighborhood total or treated as net supply. The assessment covers the ZIP rather than a property impact radius; it does not forecast prices, rents, taxes, parking rates, occupancy or growth. Transit/street improvements, adopted zoning and property-specific views remain evidence gaps until appropriate sources or site analysis exist.

The website includes a blurred Pro teaser for unconnected topics, currently transport, zoning and prices/rents/rates. Null-score factors remain in the API for explicit coverage semantics but are excluded from the free score grid. Decorative placeholders are hidden from assistive technology and contain no real data. The Upgrade to Pro action opens an accessible native dialog explaining that the topics cannot yet be unlocked and showing existing proposed pricing; it does not collect payment or unlock reports. Real data connectors, licensing, paid report generation, checkout and server-side access enforcement remain future work. The free report retains useful permit evidence and its partial-source warning; absent data must not be misrepresented as an existing paid result.

The shared summary contract adds `impactSummary.changesSummary`, separate from the conditional `overview`. The former describes a largest individual housing addition and height mentions without summing units or assuming they belong to the same building; the latter describes possible implications. The website presents these in that order and uses everyday language. The snapshot does not include a separate source disclosure or score-explanation section.

## Free transit, public projects and noise context

`lib/transit.mjs` owns a distinct current-route connector; `/api/transit?zip=` validates the five enabled ZIPs before any source call and queries the official King County Metro ArcGIS route layer with current/in-service filters. It rejects errors/truncated payloads, clips valid polylines to documented ZIP-vicinity envelopes, coalesces concurrent lookups and caches successful results for six hours. Requests time out after ten seconds. `ProjectMap` enables a toggleable purple bus-route layer on the website report; extension maps stay compact. Failure affects only the overlay and offers retry. The legend says ZIP vicinity because envelopes are not postal boundaries. Current geographic routing is not live service, future openings, guaranteed access or easier transport. Preserve the King County attribution; GIS terms permit copying/use but prohibit selling the information without written agreement. This context stays in the free report; do not include county data in a paid export without resolving those rights.

`lib/project-details.mjs` extends existing permit normalization/ranking: civic work can survive routine-alteration filtering, while apartment parking and private amenities do not become public-project claims. The summary includes `decisionSignals` and up to six `civicProjects` from the entire visible set before the fifteen-highlight cap. Conservative explicit completion phrases produce nullable `timeline` labels; issue/expiry/review/start dates never supply an expected completion. Ambiguous ranges and negated targets stay unknown. This does not add an inferred construction-duration model or turn the building-feed `CompletedDate` into a forecast. Database-backed ingestion must be refreshed to admit newly eligible civic permits.

`lib/public-projects.mjs` has a separate responsibility: a small manually reviewed directory of city parks/utility project facts (98101/98103/98104), including official URLs, source-update dates when available and review expiry. The API includes `publicProjects` even during a permit-source outage. It does not claim citywide completeness or automatic project-page ingestion. Public cards preserve estimated/phase/program target semantics, mark elapsed targets as unconfirmed and never infer a final opening from a phase date. Reviewed references expire on 2027-01-19; permitting data still works afterward.

`lib/soundscore.mjs` and `/api/soundscore?lat=&lng=` implement an optional HowLoud adapter using server-only `HOWLOUD_API_KEY`. `Soundscore` has its own UI boundary for user-triggered location requests. A listing location or explicitly selected map point is required; no ZIP centroid or average is invented. Requests are restricted to Seattle coordinates, time out after eight seconds, send the key only in a provider header and never persist/cache scores. API responses set private/no-store. Missing configuration, provider quota errors and missing/malformed scores produce explicit states without billing or Pro gating. Official docs show both object and array results; both are validated within the provider’s 50–100 scale. The free plan advertises single webpages, fewer than 2,500 queries/month and no caching. Register/configure an authorized partner key and verify account terms before real acceptance; distributed quota and endpoint-abuse protection remain before public deployment. No key or paid account has been provisioned, and real-provider scoring is not yet validated.

Medical care extends the reviewed ZIP profile, with named facilities, official destination links and Nearby labels. This is location reference data, not a care recommendation, insurance/availability claim or provider rating. Fremont uses the current clinic address at 459 N 35th St, rather than an older 400 N 34th St address.

## Permit decision signals for residents and businesses

Implemented in the existing `lib/project-details.mjs` and `lib/ranking.mjs`, with no new connector or parallel report path. The summary API adds `decisionSignals`, derived from all visible projects before the fifteen-highlight cap, using only permitted/in-review/early-proposal stages. Each card has an id, count, concrete metric, factual scope, audience tags, distinct home/business takeaways and up to three expandable project examples. Examples for maximum-value metrics put the matching maximum project first. Counts describe the available canonical project set, can retain unresolved duplicate records and are not a complete inventory.

Combine density and the indirect local-economy point into **Homes & local activity**. Add **Building height**, **Shops & everyday services**, **Commercial space & reuse**, **On-site parking**, **Demolition & site work**, and **Access & building upgrades**. Only supported cards render. The website switches among All/home/commercial views, changes takeaway text and prioritizes commercial signals in business view. The extension consumes the same server contract and displays up to four compact title/metric highlights, without repeating extraction logic or taking on backend research. Legacy impact-score metadata stays compatible; the repetitive three-score UI is replaced by actual permit facts.

Business-use matching reads a conversion’s proposed destination rather than its old use, omits explicit absent/retained/demolished uses, and distinguishes fit-outs from use changes. Existing business alterations can be useful evidence without implying a new tenant or business opening. Eligibility now includes explicit commercial-use work and seismic/access/fire-system upgrades; home maintenance, sign-only work and closed/cancelled permits remain filtered. Database snapshots need re-ingestion to acquire these newly eligible permits; no schema migration is needed.

Housing and parking values are largest individual mentions, never added into area totals or net gains. Parking distinguishes explicit no-parking proposals/removal and excludes bicycle counts; it cannot establish street availability or loading rights. Demolition/site-work mentions imply only potential disruption if work proceeds, with no invented start date or ongoing-noise claim. Retrofitting/access work is evidence of scope, not completed compliance or a building-safety grade. Views/privacy need property geometry; commercial opportunity, footfall, demand, vacancy, rents, ROI, crime and school quality are not inferred. Public-infrastructure cards, the map position, transit overlay, medical profiles and optional noise integration keep their existing responsibilities.
