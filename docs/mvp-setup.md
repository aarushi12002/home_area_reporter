# Home Area Reporter

ZIP-based research: What documented development, transit, public investment and parking activity is shaping this area?

Status: implemented Seattle batch reporting on the existing Next.js/PostgreSQL stack, with 31 reviewed city-intersecting Census ZIP areas, citywide source downloads, per-ZIP atomic snapshots, SQL pagination and full neighborhood context. Free Neon production provisioning, migrations and two complete citywide refreshes are complete; deployment and manual scheduled-workflow acceptance have passed and are recorded in the Seattle release section below. The 2024 ACS baseline is live for 33,772 ZCTAs; Washington expansion infrastructure and Tacoma/Redmond backfill adapters are implemented below; additional full-city publication, national named-place publication, paid reports and Chrome 0.5.1 review remain separate milestones.

## Product
- The website starts with **About this ZIP**: present-day local character, named workplaces/institutions, transport, groceries/shopping and medical care. This is distinct from proposed-change analysis and precedes the neighborhood snapshot. Selective highlights cover all 31 reviewed areas in `data/service-areas.json`; outside-ZIP institutions carry a Nearby/postal-code label.
- Chrome popup on Redfin/Zillow with up to fifteen highlights, plus direct website ZIP entry and full report.
- Service-area metadata preserves the reviewed 31-area Seattle registry alongside the statewide review inventory; database publication determines availability. Adding coverage is configuration plus a jurisdiction connector, not a validation-regex change.
- Free area brief first. Pro pricing: $10 single property report / $20 five-report bundle; guest checkout. Pricing does not imply all source categories are integrated.
- No comparison or favorites in MVP.

## Current request flow
1. Website/extension accept a five-digit string and the backend resolves coverage. `/api/service-areas` exposes readiness, covered jurisdiction scope and section availability; it does not advertise every syntactically valid ZIP as supported.
2. The extension reads listing JSON-LD after invocation, sends ZIP plus explicitly opted-in location only, and opens the same backend report. Listing URLs never leave the extension.
3. Background batches download both registered Seattle feeds citywide, validate counts/pagination, quarantine malformed or out-of-city records, normalize/group per jurisdiction and ZIP, then replace source evidence/projects/summary in one ZIP transaction.
4. `/api/area-summary` reads the current stored summary (15 highlights, counts/impacts, generation, publication time, freshness, covered jurisdictions) and joins current reviewed neighborhood/public-project facts. ZIP-only responses cache for five minutes; coordinate-bearing responses are private/no-store.
5. `/api/projects` executes bounded SQL keyset pagination (20 default, 50 maximum) with generation/location/visibility-bound cursors. Publication invalidates old cursors with HTTP 409 `REPORT_UPDATED`; the website reloads its summary/list. `/api/projects/:id` accepts an optional generation for consistent detail reads. Lists remain queryable without geometry; project markers cap at 100.
6. `/map` remains the compact extension map. `/api/report` is a development-only legacy diagnostic and returns 410 in production. No production page request initiates permit crawling. Only the original 98101–98105 ZIPs retain a database-free development preview.
7. Missing publication returns 202 `REPORT_PREPARING`; unsupported/malformed ZIPs return 400; unavailable storage returns 503; successful empty reports remain distinct. Reports older than 48 hours show their last publication with an awaiting-update label.
8. Optional imported ACS baselines can serve a separate historical neighborhood summary outside permit coverage. No importer activation, ZIP acceptance or payment changes local permit evidence.
9. Print/save-PDF remains a browser action; there is no server PDF/email/checkout. The read-only MCP adapter shares stored report composition and project repositories with the website.

## Public MCP adapter — issue #7

The MCP display title is **Home Area Reporter for Redfin & Zillow**, describing an independent neighborhood companion for those home searches. Keep the stable server identifier, four tool names and endpoint URL unchanged; client plugin display metadata is managed separately from protocol metadata.

Implemented `/mcp` on the existing Node.js Next.js/Vercel stack using pinned `@modelcontextprotocol/server` 2.4.0 and Zod schemas. The official SDK handler serves modern 2026-07-28 requests and stateless 2025-era compatibility; legacy initialization is tested against 2025-11-25. There are no protocol sessions or standalone GET/SSE streams. SDK behavior handles protocol negotiation and errors; the route adds origin, request-limit and activation boundaries. See [SDK compatibility guidance](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/support-2026-07-28.md).

`list_supported_zipcodes({zip?})` returns reviewed project areas/readiness, or baseline availability for an individual ZIP. It does not enumerate the national dataset into one result. `get_zip_summary({zip})` returns the shared stored report and absolute website link; `list_projects({zip,cursor?,generation?,limit?})` returns 20 projects by default, at most 50; `get_project({id,generation?})` returns published evidence. ZIPs are five-character strings, including leading zeros. MCP results have `status`, optional `data`, and safe `code`/`message` fields on errors; statuses distinguish ready, preparing, unsupported, unavailable, not_found and error. Freshness, original stages, source URLs, covered jurisdictions and observation periods remain in data. Successful empty projects differ from baseline-only areas without connected permits. Generation conflicts preserve `REPORT_UPDATED` for a summary/list restart.

All four tools declare read-only, non-destructive behavior and no authentication. The server uses internal stored services without HTTP loopback, ingestion, live fallback, Soundscore calls, exact listing context or browser Analytics. Source descriptions remain quoted evidence and are explicitly labeled untrusted in tool/server instructions. No LLM or paid API call is needed to operate the server. ChatGPT is the first real-client acceptance target; its [official connection workflow](https://developers.openai.com/api/docs/guides/custom-mcp-server) supports No authentication. A connection does not establish directory publication or deep-research/company-knowledge compatibility; `search`/`fetch` and custom UI are deferred.

`MCP_ENABLED` defaults off; a private `MCP_RATE_LIMIT_SECRET` of 32+ characters and migration `0003_mcp_rate_limits.sql` are required to enable requests. `MCP_ALLOWED_ORIGINS` lists exact accepted browser origins; absent Origin is allowed for machine clients. Production trusts Vercel-overwritten client IP only when VERCEL=1; unsupported production proxies fail closed. The `mcp_rate_limits` table contains HMAC bucket IDs, minute windows and bounded counters, never raw IPs or tool arguments. Shared limits are 60/minute per connection IP and 300/minute globally; exhausted callers receive 429 and Retry-After. Counters expire at one hour; physical deletion occurs on the next MCP request, so expired rows may remain during inactivity. Client IPs can be shared by AI-provider relays. Request bodies cap at 64 KiB, serialized tool results at 256 KiB with short text and structured data, and tool/handler waits at 15 seconds. Responses are private/no-store; raw database errors and credentials never enter tool responses. Provider logs retain their own policies. Monitor limits, safe error counts and latency without persisting conversation arguments.

Rollout: migrate, configure the target environment, verify protocol/Inspector behavior and Vercel machine access, then prove a real ChatGPT question-to-evidence workflow. Until those checks pass, leave public activation disabled and record the exact blocker. Rollback is `MCP_ENABLED=false` plus redeployment; the additive counter table can remain. Existing reports and batch ingestion are independent of MCP activation. Update issue #7 with actual test/deployment receipts; do not infer compatibility from a build alone.

## Evidence and model boundaries
`lib/zip-profile.mjs` owns the manually reviewed current-area directory. It uses short name/address facts and original descriptive sentences from official company, institution, retailer and transit pages, with no listing-site copy, ratings, commute estimates, hours, salaries or automated POI/GTFS ingestion. This is editorial reference data, separate from source-record ingestion. Location addresses/postal codes remain in the response for review; mismatched postal codes are explicitly Nearby, and routes/stations are labeled as serving the area rather than guaranteeing proximity to a listing. Profiles carry per-ZIP review dates: the original five expire on 2027-01-19 and the 26 additions on 2027-01-22; unsupported ZIPs, invalid dates and future-dated reviews return null. Existing permit/report behavior continues when a profile expires. Source expansion remains planned as described below; this directory does not establish a complete transit connector or complete business coverage.

No LLM is used. Official descriptions and original status are shown with conservative stage labels. Available source dates are event dates, not update dates; retrieval timestamps are separate. The shared summary builder adds `impactSummary` for both persistence and live fallback: conditional implications of recorded housing additions and building heights, with up to two supporting project links per topic. It uses all visible current projects before the highlight cap, excluding uncertain-stage and demolition-only projects from positive implications. Each factor includes a concise `takeaway` and a nullable `score`. The 1–5 record-support rubric adds one point each for a project, an official link, a numeric housing/height field, multiple projects and a permitted project; indirect economic implications are capped at 2. Missing evidence is `null` and displayed as an em dash. These are transparent ordinal record signals, not impact-severity, benefit, confidence-percentage or market-outlook scores. This legacy `impactSummary.items` score metadata remains in the API for compatibility; the website now uses grouped `decisionSignals` with concrete counts and single-plan metrics. Scoring methodology and data-origin explanations remain outside the snapshot UI. Individual project cards keep their city-record links, and partial source coverage remains visible.

Building-height mentions are descriptive evidence, not a confirmed change in height or view obstruction. Unit counts remain per project, never summed into a neighborhood total or treated as net supply. The assessment covers the ZIP rather than a property impact radius; it does not forecast prices, rents, taxes, parking rates, occupancy or growth. Transit/street improvements, adopted zoning and property-specific views remain evidence gaps until appropriate sources or site analysis exist.

The website includes a blurred Pro teaser for unconnected topics, currently transport, zoning and prices/rents/rates. Null-score factors remain in the API for explicit coverage semantics but are excluded from the free score grid. Decorative placeholders are hidden from assistive technology and contain no real data. The Upgrade to Pro action opens an accessible native dialog explaining that the topics cannot yet be unlocked and showing existing proposed pricing; it does not collect payment or unlock reports. Real data connectors, licensing, paid report generation, checkout and server-side access enforcement remain future work. The free report retains useful permit evidence and its partial-source warning; absent data must not be misrepresented as an existing paid result.

The shared summary contract adds `impactSummary.changesSummary`, separate from the conditional `overview`. The former describes a largest individual housing addition and height mentions without summing units or assuming they belong to the same building; the latter describes possible implications. The website presents these in that order and uses everyday language. The snapshot does not include a separate source disclosure or score-explanation section.
